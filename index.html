Presentación del Proyecto

MediConnect es un sistema de salud digital que conecta pacientes, médicos y administradores mediante citas, historiales clínicos, videoconferencias y facturación electrónica. Este sitio documenta su arquitectura siguiendo estrictamente el paradigma 4+1 UML con diagramas descriptivos, interpretaciones técnicas y trade-offs adoptados.

  • Arquitectura basada en dominios: Paciente, Médico, Cita, Historial, Pago, Teleconsulta.
  • Infraestructura cloud-native con despliegue contenerizado.
  • Seguridad: TLS 1.3, AES-256, JWT, OAuth2.
  • Disponibilidad objetivo: 99.9% en horario hábil.

Requerimientos del Sistema

Matriz RF1-RF4 y RNF1-RNF2 con prioridad y complejidad.

Requerimientos Funcionales (RF)

ID Requerimiento Prioridad Complejidad
RF1Gestión y Agendamiento de CitasAltaMedia
RF2Registro de Historial ClínicoAltaAlta
RF3Módulo de Videoconferencia MédicaAltaAlta
RF4Procesamiento de Pagos y FacturaciónMediaMedia

RF1 — Gestión de Citas

El paciente busca profesionales por especialidad, filtra disponibilidad horaria y confirma reservas. El médico recibe confirmaciones y gestiona su agenda.

RF2 — Historial Clínico

El médico consulta y actualiza fichas médicas, registra diagnósticos y emite recetas digitales con trazabilidad completa.

RF3 — Videoconferencia

Teleconsultas en tiempo real con audio y vídeo de alta calidad, integradas directamente desde la ficha del paciente.

RF4 — Pagos y Facturación

Procesamiento de transacciones mediante pasarela de pago, generación de comprobantes digitales y conciliación bancaria.

Requerimientos No Funcionales (RNF)

IDRequerimientoPrioridadComplejidad
RNF1Alta Disponibilidad Operativa (99.9%)AltaAlta
RNF2Seguridad y Confidencialidad de DatosAltaMedia

RNF1 — Alta Disponibilidad

Uptime del 99.9% durante horario hábil. Arquitectura con failover automático, balanceo de carga y redundancia de servicios críticos.

RNF2 — Seguridad

TLS 1.3 para tránsito, AES-256 para reposo. Cumple normativas sanitarias y protección de datos personales (HIPAA / GDPR).

VISTA DESARROLLO

Diagrama de Componentes — Modularidad

Interpretación técnica

El código se organiza en componentes contenerizados. API Gateway expone endpoints REST y enruta a servicios internos. Cada dominio opera como servicio independiente con su propia base, permitiendo despliegue independiente.

  • Auth Service: JWT / OAuth2.
  • Patient Service: citas y disponibilidad.
  • Medical Service: historiales y recetas.
  • Billing Module: pasarela de pagos.
  • Teleconsult Module: videoconferencia.

Interpretación técnica

VISTA FÍSICA

Diagrama de Despliegue — Topología

Interpretación técnica

La infraestructura es cloud-native. Cloudflare CDN protege y acelera el tráfico. Un load balancer NGINX distribuye a servidores activos con sticky JWT. La base de datos PostgreSQL opera con réplica asíncrona y Redis gestiona sesiones y caché. Archivos médicos se almacenan en S3.

  • Servicio activo / standby para alta disponibilidad.
  • PostgreSQL Primary + Réplica ASYNC.
  • Redis para sesiones y rate limiting.

Conclusiones y Trade-offs

Decisiones arquitectónicas adoptadas y sus implicaciones.

Arquitectura Hexágona (Ports & Adapters)

Separación clara entre dominio, aplicación e interfaces. Faculta testing independiente y cambios de tecnología sin afectar el núcleo.

  • Testing unitario sin base de datos.
  • Cambio de proveedor de pagos sin tocar dominio.
  • Principio de inversión de dependencias cumplido.

Microservicios vs Monolito

Elegimos microservicios por escalabilidad independiente por dominio (citas vs pagos vs historial).

  • Deploy independiente: menor riesgo de regresión.
  • Complejidad de red y consistencia eventual aceptada.
  • Requiere observabilidad fuerte (logs, trazas).

Consistencia Eventual vs ACID

Historial clínico tolera lag de segundos (eventos). Casos críticos (pagos, recetas) usan transacciones ACID.

  • Eventos de dominio sincronizan duplicados.
  • Riesgo: datos inconsistentes temporalmente.

Duplicación vs Normalización

Datos duplicados en cada microservicio para aislar dominios, evitando locks globales.

  • Aísla fallas de un servicio.
  • Aumenta complejidad de sincronización.
